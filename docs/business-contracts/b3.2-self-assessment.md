# BCD：B3.2 交接自评不静默丢弃（assessments 结构校验 + 覆盖留痕）

- 关联规范：skills/agent-kanban/SKILL.md「交接与等待」（门序 7 / 交付自检 / 收尾协议）；docs/business-contracts/distill-pipeline.md §3 Commands 3（request_review 条款）；docs/business-contracts/b3-dispatch-loop.md §7 I4（A4② 提醒级、无服务端门——本批把其中「自评」一支升级为服务端门）
- 版本：v1（2026-10-29，B3.2 开工）

## 1. 客户原话语义分析

客户原话（2026-10-29，B3.1 批收尾时选定本批）：

> 「按照你的建议走」（建议＝修 `assessments` 静默丢弃；理由：试用期三问第 1 问「对照预期验收」能不能拿到数据，取决于自评落不落得进板面）

支撑本批的实测证据（B3.1 批，需求 `29f06424`，批外留证 `/home/shih/.tmp-ak-m16/b31-g28/ledger.md`）：

1. 三条 B3 dogfood 需求 `acceptance=[]` —— 零锚，无法验（known-gaps G27(a)）。
2. B3.1 需求**有** 6 条验收锚，返工意见里也**明写**「这次请逐条对锚自评」，worker 照做了，但提交的 `assessments` 是扁平形态（`{item, state, reason}`，缺 `subtask_id` 与 `items` 嵌套）。
3. `_persist_self_assessment` 对不认识的形态逐条 `continue`：**不报错、不写事件、payload 不留原始输入**。worker 以为交了自评，板面看起来「没交」，服务端返回成功。
4. 后果：`acceptance_table` 的 `state` 停在 `null`，交接时刻无法回答「符合预期吗」；评审被迫读原始输出（反黑箱失效）。

即：不是 worker 不执行（A4② 软约束失效那类），是**执行了被系统静默吞掉**，worker 连自纠机会都没有。

## 2. Impact Mapping

- **Why**：C1「默认视图回答三问」的第 1 问（对照预期验收）依赖 `subtasks.acceptance[].state`；静默丢弃让这一问在数据层就无答案，且失败不可见（双方都不知情）。
- **Who**：worker（自评提交方，获得可自纠的错误信息）；人（评审时看到覆盖摘要与逐项状态）；后续批次（B4 展示面消费 payload 摘要）。
- **How**：`request_review` 增服务端结构校验（形态 + 归属 + 覆盖），拒写整单并给可自纠信息；payload 增覆盖摘要；SKILL 与 MCP description 同步正典形态。
- **What**：见 §3 Commands 与 §7 不变量。

## 3. Domain Event 流

事件 kind（12 个）不变，不加表不加列；`subtasks.acceptance` 是既有 JSON 列（条目已含 `state` / `deviation_reason` 槽位）。

- **SelfAssessmentReceived**（不是新事件，是 `review_request` 的 payload 扩展）：`payload.assessment = {required, covered, added, received_subtasks, received_items}`（全整数，纯派生计数）。
  - `required`＝本需求**非 abandoned** 子任务的验收条目总数（覆盖分母）
  - `covered`＝本次落库的既有条目数（命中验收文本的）
  - `added`＝worker 自拟新增条目数（子任务原先无此验收文本）
  - 只增不改：既有 `evidence` / `summary_line` 键不动；`awaiting_human` 形状不动。
- 写入语义：先全量校验、后落库（两遍），保证「拒写＝零写入」（不出现部分子任务已改、后一项才报错的半态）。

## 4. BDD Given-When-Then 场景

### S10（happy）：全覆盖自评落库 + 覆盖摘要留痕
- Given：需求 CLAIMED，两个非 abandoned 子任务各 1 条验收条目（Y1 / Y2）
- When：`request_review(evidence=..., summary_line=..., assessments=[{subtask_id: s1, items:[{item: Y1, state: met}]}, {subtask_id: s2, items:[{item: Y2, state: not_met, deviation_reason: "只跑了单测"}]}])`
- Then：成功；`get_task_detail.subtasks[*].acceptance[*].state` 分别为 met / not_met（后者带 deviation_reason）；`review_request.payload.assessment == {required: 2, covered: 2, added: 0, received_subtasks: 2, received_items: 2}`。

### S11（edge）：形态不合法 -> 整单拒写 + 可自纠
- Given：同上
- When：`assessments=[{"item": "Y1", "state": "met"}]`（扁平形态，缺 `subtask_id` / `items`）
- Then：`invalid_record`；错误消息含：第几项、缺什么、**正典形态示例**（一条可直接照抄的 JSON 片段）、本需求可用 `subtask_id` 与验收条目清单；`subtasks.acceptance` 与调用前逐字相同（零写入）；`awaiting_human` 未设置；无 `review_request` 事件。

### S12（edge）：漏评 -> 拒写并点名漏项
- Given：两个子任务共 2 条验收条目，其中 1 条 `links_to` 需求锚
- When：assessments 只覆盖 1 条
- Then：`invalid_record`，消息列出未覆盖的 `subtask_id` + 条目文本，并提示两条出路：补评，或先 `update_subtask(state=abandoned)` 把不再需要的子任务排除出分母。零写入。

### S13（edge）：子任务归属错 / 自拟条目
- Given：需求 A 认领中；另一需求 B 的 `subtask_id`
- When：assessments 引用 B 的 subtask_id
- Then：`invalid_record`（不得静默跳过），消息含本需求可用清单。
- Given：子任务无验收条目
- When：`items=[{item: "自拟：实现可回滚", state: "met"}]`
- Then：接受；该条目被追加为子任务验收条目（既有语义保留）；`payload.assessment.added == 1`，`required == 0`。

### S14（backward）：无验收条目且未传 assessments
- Given：纯调研/决策类需求（无子任务或无验收条目）
- When：`request_review(evidence=..., summary_line=...)`（不传 assessments）
- Then：成功，`payload.assessment == {required: 0, covered: 0, added: 0, received_subtasks: 0, received_items: 0}`（字段恒在，便于 B4 消费与审计）。

### S15（edge）：有验收条目但不传 assessments —— 省略不构成豁免（v2 折入盲审 P1）
- Given：需求 CLAIMED，子任务 1 条验收 `Y1`
- When：`request_review(evidence, summary_line)`（不传 assessments，或显式传 `None`）
- Then：`invalid_record`（漏评 `Y1`，消息含可用清单 + 两条出路）；零写入。
- 边界：只有「无验收条目」时省略才合法（S14）。三种输入 `不传` / `None` / `[]` 行为必须一致：有验收条目即拒，无验收条目即成功。

### S16（edge）：deviation_reason 双向一致（v2 折入盲审 P2-3）
- Given：子任务有验收 `Y2`
- When：`state="not_met"`（或 `"deviated"`）且 `deviation_reason` 缺失 / 空 / 纯空白
- Then：`invalid_record`，消息给 `assessments[i].items[j]` 定位 + 「not_met/deviated 必须给 deviation_reason」+ 形态示例；零写入。
- When：上一轮 `Y2` 落库为 `not_met + "只跑了单测"`，本轮提交 `state="met"` 且不给原因
- Then：成功，落库 `{"item": "Y2", "state": "met"}` —— **旧 `deviation_reason` 被清除**（不留上一轮原因，E10「以最新自评为准」）。

### S17（edge）：重复引用 / 重复条目 / 已 abandon 的子任务（v2 折入盲审 P2-2）
- When：同一 `subtask_id` 在 assessments 出现两次；或同一子任务 `items` 内同一 item 文本出现两次
- Then：`invalid_record`，消息给 `assessments[i]` / `assessments[i].items[j]` 定位并指明「重复」；零写入。
- When：assessments 引用已 `abandoned` 的子任务
- Then：`invalid_record`，消息说明该子任务已放弃、不计入覆盖分母，如需评估先 `update_subtask` 改回。
- 配套计数不变式见 I11。

### S18（edge）：字符串形态的既有验收条目（v2 折入盲审 P2-4）
- Given：`add_subtask(acceptance=["实现可回滚"])`（历史数据/外部写入的裸字符串形态）
- When：提交 `{"item": "实现可回滚", "state": "met"}`
- Then：成功，落库 `[{"item": "实现可回滚", "state": "met"}]`（不出现同文本双份）；`required=1, covered=1, added=0`。
- 归一语义与 `operations_util.normalize_anchors` 同口径（str -> `{"item": str}`），不另造一套约定。

### S19（edge）：体积门（v2 折入盲审 P2-5）
- When：`review_request` 组装的事件 payload 超 8 KB（如 summary_line 极长），或自评落库后某子任务 `acceptance` 超 8 KB
- Then：`invalid_record`，零写入（与 `add_subtask` / `add_record` / `update_progress` 同口径 `_check_payload_size`）。

## 6. Premortem（假设 6 个月后失败）

1. **门太硬挡住合法交接**：验收条目过期/与交付物不对应时 worker 卡在 `invalid_record` 反复试错。
   缓解：错误消息给全可用清单 + 两条出路（补评 / abandon 子任务）；SKILL 同步文档化。残余：条目语义过期仍要人改 `set_expectations`（不在本批）。
2. **自拟条目滥用**：worker 给子任务新增宽松条目自评 `met`，制造「看起来达标」。
   缓解：`added` 计数进 payload 可审计；真实锚（`requirement.acceptance`）仍由人设、`links_to` 约束不变。残余：`added` 无展示面（B4）。
3. **只落数据不落人眼**：payload 摘要无人读，人仍不知道覆盖情况。
   边界：本批只保证数据在板面可查（detail/export）；摘要视图呈现归 B4（G3 门禁未开）。
4. **形态再漂移**：SKILL / MCP description / PRD 三处表述不一致，worker 又按旧形态提交。
   缓解：本批把正典形态写进 SKILL + MCP docstring；校验消息自带上例（带内兜底）。
5. **门越收越紧变成试错循环**（v2 新增风险）：8KB 体积门 / 重复拒写 / abandoned 拒评三条一起上，worker 可能连撞 3 次 `invalid_record` 才交接成功。
   缓解：全部错误消息带 `assessments[i].items[j]` 定位 + 具体原因（不是泛化的「形态错」）；单次交接的字段量级（几十条）远离 8KB。残余：错误消息齐全但仍要看懂——交给 T3 试用观察（真机卡顿计数）。

## 7. 业务不变量

强不变量（违反＝业务失败）：

- **I6 自评不静默丢弃**：凡提交 `assessments`，要么整单落库（含覆盖摘要），要么整单拒写并返回可自纠信息；禁止静默跳过任何一项、禁止部分落库。违反后果：worker 认为已交、板面为空、C1 第 1 问无数据，双方都不知情（B3.1 实测）。
- **I7 逐项闭合**：有验收条目（非 abandoned 子任务）就必须逐项给出 `state`；漏项即拒写。**省略 `assessments` 不构成豁免**——只有「无验收条目」时省略才合法（v2 折入盲审 P1）。**空白/空文本验收条目不进分母**（v3：这种条目无法被逐字匹配——提交同样文本必被判「缺 item」——计入分母会让需求永久卡在漏评，唯一出路是 abandon 子任务）。违反后果：验收对照表停在 `null`，评审被迫读原始输出，反黑箱承诺失效。
- **I8 拒写零写入**：校验失败时 `subtasks.acceptance` / `awaiting_human` / 事件链逐字不变（先校验后落库）。违反后果：半态自评混进板面，比不交更难查。
- **I9 既有形态兼容**：仓内既有 4 处自评用例（ac_cases_b/c/e/g）形态不变仍绿；无验收条目的需求可省略 `assessments`。v2 例外一处：`ac_cases_c:35` 的 `not_met` 自评补上线内 `deviation_reason`（I7 之外的必填字段，形态不变）。违反后果：存量回归红，说明契约变更越界。
- **I11 计数不变式**（v2 折入盲审 P2-2）：任何成功路径必须满足 `covered <= required` 且 `covered + added == received_items`（同 subtask/item 不重复计数）。违反后果：`payload.assessment` 自相矛盾，B4 展示面据此算覆盖率会算出 >100%。

软约束（违反可容忍）：

- **I10**：自评内容（state 选得对不对）仍靠人抽查——本批只保证「提交的内容完整落库且可审计」，不判断真实性（G2 既有残余）。

## 9. MCP description 正典形态（逐字，实现者照抄）

```
    参数: requirement_id（32 位全 id 或 8~31 位唯一前缀，空白/大小写/连字符不敏感）, evidence（pr_url/commit_range/test_summary 至少一项）,
          assessments＝逐项验收自评，形态 [{subtask_id: <子任务 id>, items: [{item: <该子任务验收文本逐字>, state: "met"|"not_met"|"deviated", deviation_reason: <not_met/deviated 必填；met 时忽略并清除旧值>}]}]；

          summary_line（交接一句话：做了什么/先看哪）。
```
